# Согласованность команд и отключения — 29.10.2026

## Исходное состояние и обоснование

Исходная версия 0.2.46: коммит `fcdc1d363880f457b88d947f8aca34a527090826`. Тесты и выпуск штатного Windows CI пройдены. Открытых PR на момент исследования не было. Продолжаем исследование пользовательского контроля из `docs/research/2026-10-26-adaptive-shortcuts.md` и исправление ручной работы без фонового процесса из `docs/research/2026-10-29-disabled-manual-actions.md`.

Подтверждённый анализом исходников дефект: `Settings::queue` сначала вызывал `start_background_if_enabled`, которая отпускала именованный mutex `startup` сразу после проверки состояния, а затем отдельным вызовом `Store::command` добавлял команду в SQLite. Параллельная команда «Отключить» захватывает тот же mutex, останавливает worker, помечает ранее ожидавшие команды как отменённые и сохраняет `background_disabled=true`. Между проверкой и поздним INSERT окно настроек могло создать **новую ожидающую команду уже после остановки**. Фоновый процесс не выполнял бы её. Это логический дефект порядка операций, а не доказательство жалобы пользователя.

Исследовательская основа: Findlater & McGrenere, CHI 2004, https://doi.org/10.1145/985692.985704 — предсказуемость и сохранение управления человеком в адаптивных интерфейсах. Независимый пример проблем с доступностью настроек в другом приложении: https://github.com/Flow-Launcher/Flow.Launcher/issues/3187. Эти внешние данные не являются свидетельствами дефекта Desktop Pilot.

## Воспроизведение на реальной логике

Новый `src/ui/queue_race_tests.rs` запускает действительный асинхронный `Settings::queue` с реальными mutex `startup` / `background`, SQLite, существующей базой профиля, настоящим `setup::disable_background`, исходным URL-ярлыком и защитой правил. Блокировка фонового mutex имитирует уже готовый worker, не запуская сторонних программ; test-only checkpoint ставится между подтверждением готовности и INSERT. Пока вызов приостановлен, другая нить пытается захватить `startup`. Если захват возможен, отключение успело бы завершиться до INSERT и команда осталась бы без исполнителя.

- Базовый тестовый коммит `67f69f8a5ff8dcb700b35e13740e1a13ab2e034e`. Первоначальный прогон `40821563873` завершился на проверке форматирования и **не** является поведенческим воспроизведением.
- Исправленный по форматированию запуск `https://github.com/TechWisard/desktop-pilot/actions/runs/40821716693`: на Windows Server 2025 тест провалился на конкретной проверке незакрытого окна mutex (287 остальных Rust-тестов прошли). Windows Server 2022 также выполняет этот прогон; статус надо проверять отдельно, без приписывания недоказанного успеха или ошибки.
- После исправления та же контрольная точка должна удерживать `startup` до подтверждённого INSERT. Следующее отключение должно отменить уже помещённую в очередь команду, не оставляя `pending`, не меняя исходный ярлык и ручное правило. Проверки версий Windows, native tests, Clippy, сборка и публикация должны пройти независимо.

## Исправление и ограничения

Включённая программа теперь стартует/проверяет готовность background, затем записывает команду в SQLite **до освобождения одного и того же `startup` mutex**. Проверка `shutdown/background_disabled` внутри write-транзакции предотвращает поздний INSERT после явной остановки. Если программа отключена, прежний непосредственный асинхронный путь без запуска worker остаётся доступным. Отмена после корректного INSERT записывает статус `error`, и интерфейс не должен ждать несуществующего исполнителя.

Никаких новых настроек, модулей слежения, постоянных кешей, зависимостей, сетевых служб или телеметрии. В тестовом билде контрольная точка исключена из release через `#[cfg(test)]`. Длительность удержания mutex на этапе SQLite INSERT не измерялась на физических устройствах; синтетический тест доказывает сериализацию, не экономию времени людей. Периферийные проверки физической Windows 11 (200%), реальных отключений SMB и многонедельной смены привычек остаются в issue #22.
