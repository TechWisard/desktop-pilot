# Prevent separating open editable documents from owner markers — 2026-11-09

## Primary sources, reported behavior, and observed source gap

Microsoft Support documents Word owner files with the `~$` prefix replacing the first two letters of the document's filename (for example `Document.doc` -> `~$cument.doc`) and describes their role in identifying another editor: https://support.microsoft.com/en-gb/word/the-document-is-locked-for-editing-by-another-user-error-message-when-you-try-to-open-a-document-in . Microsoft Q&A also describes owner files as temporary companion records that should not be deleted while a document is open: https://learn.microsoft.com/en-us/answers/questions/4822723/what-are-doc-and-docx-can-you-open-them-or-delete . LibreOffice uses distinct `.~lock.<filename>#` companions; end-user discussion confirms these can remain after abnormal exits: https://www.reddit.com/r/libreoffice/comments/1k3c2da/ . These sources explain real editing workflows, but **do not constitute a report of a Desktop Pilot data-loss bug**.

Confirmed code gap at the unreleased organizer head: opt-in classification accepts ordinary `.doc`, `.docx`, `.odt`, `.ppt`, `.pptx` and `.rtf` files. The existing associated-file guard recognizes media sidecars, archive parts and `*_files` folders, but not Microsoft Office or LibreOffice document lock names. A non-hidden, otherwise readable `~$cument.docx` therefore qualified as an ordinary document; its real `Document.docx` could be moved independently while the edit marker stayed or was moved. The hidden attribute usually excludes Word owner markers, but depending on attributes and stale lock state this protection cannot be assumed. An editable file can also have a readable shared handle; this change uses the filename relationship as independent conservative evidence.

## Tested scenario and scoped fix

Recognize exact sibling lock patterns using the same bounded, read-only directory snapshot and do not read or delete their contents. Never propose a recognized `~$` owner file itself. Keep its matching editable source in place, including an owner marker that replaces the first two filename characters. Honor an exact LibreOffice `.~lock.<filename>#` marker. An ambiguous Word suffix deliberately protects all potentially matching documents; independent editable documents and ordinary PDF/TXT remain eligible.

Synthetic production-path Windows + SQLite tests create ordinary (non-hidden) owner files and documents, analyze an actual optional-file plan, apply independent moves, and Undo. Before the guard, the Word owner file and the opened document would appear as eligible moves; afterwards neither is proposed, while two independent documents and two site shortcuts still move and are restored exactly. A second test adds a matching marker **after preview**: Apply must reject the whole stale plan before any folder or rename. The unchanged marker and opened file retain their byte contents; manual policies, worker state and saved history must stay untouched. Unit tests also cover ambiguous names, case differences, false-positive boundaries and 6000-item snapshots.

This prevents a class of unsafe proposed moves; it does not detect every document lock protocol or prove that real people saved time. No new settings, background behavior, telemetry, extension scanning or external access. Keep this change on the unreleased 0.3.0 integration branch until full Windows/Explorer/UI checks and the outstanding physical acceptance conditions pass.
